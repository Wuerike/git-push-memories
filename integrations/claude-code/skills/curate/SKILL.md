<!-- managed-by: git-push-memories -->

Curate one to sixteen proposals only because the user explicitly invoked `/curate`. Every proposal may be consumed into canonical memory or discarded with a closed reason code.

1. Call `memory_proposal_list` exactly once. Do not treat a proposal as canonical memory.
2. If the user supplied proposal IDs, select only their exact matches, preserving their order. Otherwise show the available proposal IDs, titles, suggested actions, and targets, then ask the user to select one to sixteen. Cancellation, no proposals, an unknown ID, a duplicate ID or more than sixteen selections ends the flow without preview or apply.
3. Show the selected proposal's exact knowledge, legacy source paths, and structured source references. For each structured repository available in a local checkout, call `memory_reference_snapshot` with that transient root, the proposal's exact full revision, and its paths; compare the returned references byte-for-byte with the proposal. For every matching reference, call `memory_reference_expand` from line 1 with `budget_bytes: 4096`, continuing only as needed for at most three chunks. Never persist excerpts or call a legacy path verified. Derive a short query from the knowledge and call `memory_search` exactly once with `budget_bytes: 4096`. Expand every returned handle, in rank order, up to three, with `budget_bytes: 4096`.
4. Classify the candidates. For `create`, choose `create_section` with an existing canonical page and a concise new heading when that page should own the knowledge; otherwise choose `create_page` with a new `memories/<category>/<lowercase-kebab-case>.md` path. For `update`, choose `replace_section` only when one expanded leaf section is the unambiguous target. Build a complete replacement body that incorporates the proposal while preserving every still-valid fact. For `remove`, choose `remove_section` for one unambiguous expanded leaf; choose `remove_page` only when that leaf is the sole canonical `Overview` of a generated page and the whole page is obsolete. Use the handle's exact path, section ID, and content hash. A proposal target is only a suggestion. Do not cascade removals or repair links automatically.
5. Classify each expanded canonical candidate and related proposal as `equivalent`, `contradictory`, `related`, or `unrelated`; present this as an assisted assessment, never as a completeness guarantee. Choose `discard_proposal` only when the proposal itself should not become memory, using exactly one reason: `not_relevant`, `incorrect`, `sensitive`, `wrong_target`, `superseded`, or `duplicate`. Use `duplicate` only when identified evidence already represents the same knowledge. Choose `keep_pending` in a multi-proposal transaction when one selected proposal remains unresolved while other decisions can proceed; it keeps that proposal byte-identical in the inbox and may not be the only batch item. Do not discard valid knowledge merely because its suggested target is wrong; select the correct canonical target instead.
6. If any candidate is classified as `contradictory`, show the conflicting candidate and ask the user to choose the resolution from only options supported by the selected proposal and identified evidence before requesting a preview. Any proposal may preserve canonical memory and be discarded. An `update` may replace an identified canonical leaf with a complete current state. A `create` may keep both facts only when they have distinct explicit scopes and can use `create_page` or `create_section`. Otherwise cancel; ambiguous or unsupported resolution ends the flow without preview.
7. Require distinct target paths for all canonical decisions; if two decisions need the same page, stop and ask the user to curate them in separate attempts. For one selected proposal, call `memory_curate_preview` exactly once with its decision. For multiple proposals, call `memory_curate_batch_preview` exactly once with one decision per selected proposal in the selected order. Include target path for canonical operations; `heading` only for `create_section`; `section_id`, `content_hash`, and complete `replacement` only for `replace_section`; `section_id` and `content_hash` for `remove_section` or `remove_page`; and `reason` only for `discard_proposal`. Any tool error ends the flow without apply or fallback writes.
8. Classify and show every canonical candidate and related proposal in the preview evidence, followed by every source reference's integrity status, the exact operation, proposal fields, target fields, replacement or discard reason, and diff. Lexical candidates and source statuses are limited evidence. `verified` proves only local repository, revision, blob path and content hash; it does not prove the claim. Assess semantic support separately as `supports`, `contradicts`, or `unclear`; the server value `not_assessed` must never be presented as support. `unavailable`, `mismatch`, and `legacy_unverified` must never be called verified. If preview evidence changes any classification, integrity status or chosen resolution, stop and require a new explicit attempt. Otherwise require explicit confirmation that this exact decision and diff may be applied and committed.
9. After confirmation, call `memory_curate_apply` exactly once for one proposal or `memory_curate_batch_apply` exactly once for multiple proposals, with only the returned preview token. For one decision, cancellation or any adjustment leaves the proposal unchanged; for a batch, it leaves every selected proposal unchanged. End the flow and start a new explicit `/curate` attempt to produce another preview.
10. Return the proposal ID, canonical target and section ID when present, decision, reason when discarded, and commit. Explain that a consumed commit contains the exact canonical change plus proposal removal, while a discarded commit removes only the proposal and records its reason. Pushing remains a human action:

```bash
git -C <memory-repository> push
```

Never call apply without a preview from this invocation or before the user confirms its exact diff. Never edit the memory repository through another tool.
